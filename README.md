# Workgine: этап 1

Один аккаунт с двумя кабинетами: заказчик и исполнитель. Переключение кабинета сохраняется на сервере и не меняет владельцев данных.

## Что работает

- Регистрация, вход, получение своего аккаунта и workspace.
- Выбор первой роли и переключение между ролями.
- Создание черновика, его просмотр и редактирование с защитой от устаревшей версии.
- Публикация заказа после проверки категории, бюджета и описания.
- Собственный список заказов; поиск чужих опубликованных заказов, категории и пагинация.
- Личный профиль исполнителя: описание и ставка.
- Изолированный доступ к черновикам и профилям.

Отклики, офферы, задачи, сдача/приемка, платежи, чат, уведомления, отзывы и споры еще не входят в работающий этап. Старые исходники этих модулей сохранены, но их небезопасные маршруты не подключены в app/main.py. Не подключайте их без доработки прав и бизнес-правил.

## Установка на Windows (PowerShell)

Нужен установленный и запущенный Docker Desktop с Linux containers. Node.js и Python на компьютере для этого способа не нужны.

1. Распакуйте архив в НОВУЮ папку, например `C:\Projects\workgine-stage1`. Не накладывайте файлы поверх старого проекта: здесь новая история миграций. Не копируйте старый `.env`.
2. Остановите старый backend/frontend, если они занимают порты 80, 8000 или 3000. Старый Compose можно остановить командой `docker compose down` из его папки. Не используйте `-v`: старые данные можно оставить.
3. Откройте терминал в папке, где лежит `setup.ps1`, и выполните:

```powershell
powershell -ExecutionPolicy Bypass -File .\setup.ps1
```

Параметр действует только для этого запуска PowerShell, системную политику не меняет. Скрипт создаст случайные локальные секреты и запустит сборку контейнеров. Первый запуск требует интернета для загрузки зависимостей и образов.

4. Откройте http://localhost. Создайте НОВЫЙ аккаунт. Готовых логинов и паролей нет.
5. Для документации API откройте http://localhost/docs.

Если порт 80 занят (IIS, Skype и т.п.), добавьте в `.env` строку `HTTP_PORT=8080` и откройте http://localhost:8080.

Создается отдельный Docker-проект `workgine-stage1` и новый том `stage1_pgdata` в его пространстве имен. Старая база не используется и не удаляется. Аккаунты из старой базы здесь не появятся.

Если страница пока не открывается:

```powershell
docker compose ps
docker compose logs --tail 100 nginx api migrate frontend
```

Повторный обычный запуск:

```powershell
docker compose up -d
```

Остановка:

```powershell
docker compose down
```

## Как устроен запуск

```
браузер ──► nginx :80 ─┬─ /api/*, /health, /docs ──► api (FastAPI, uvicorn, 2 процесса)
                       └─ всё остальное ──────────► frontend (Next.js standalone)
migrate (разовый) ──► alembic upgrade + seed ──► db (PostgreSQL)
```

- Наружу опубликован только nginx. `api` и `frontend` доступны лишь внутри сети Docker.
- Фронт обращается к API по относительному адресу `/api/v1`, поэтому один образ работает на любом домене, а CORS не нужен.
- Миграции выполняет отдельный сервис `migrate`. `api` стартует только после его успешного завершения.
- Все контейнеры работают не от root, перезапускаются после сбоя, логи ротируются (5 файлов по 10 МБ).
- nginx ограничивает вход и регистрацию: 10 запросов в минуту с одного IP, дальше ответ 429.
- Настройки в `.env`, образец в `.env.example`.

## Публичный сервер (домен + HTTPS)

Нужен Linux-сервер с Docker, DNS-запись домена на его IP и открытые порты 80 и 443.

```sh
DOMAIN=workgine.kz LETSENCRYPT_EMAIL=admin@workgine.kz ./setup-prod.sh
```

Скрипт создаст `.env` со случайными секретами, выпустит сертификат Let's Encrypt и запустит стек с `docker-compose.prod.yml`. В этом режиме:

- HTTP перенаправляется на HTTPS, включены HTTP/2 и HSTS;
- сертификат продлевается автоматически (сервис `certbot`), nginx перечитывает его раз в 6 часов;
- Swagger выключен (`DOCS_ENABLED=false`), API работает в 4 процессах;
- раз в сутки делается дамп базы в `./backups`, хранятся 14 дней.

Обновление на сервере:

```sh
git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Восстановление из дампа:

```sh
docker compose exec -T db pg_restore -U workgine -d workgine --clean < backups/<файл>.dump
```

## Разработка без Docker

Backend: `pip install -r requirements-dev.txt`, затем `uvicorn app.main:app --reload`. Frontend: `npm run dev` в папке `frontend`; запросы на `/api` Next перенаправит на http://localhost:8000.

## Как проверить самому

1. Зарегистрируйте аккаунт A. Выберите «Заказать услугу».
2. Создайте заказ. Сохраните черновик и откройте редактирование. Поменяйте заголовок и сохраните.
3. Укажите категорию, положительный бюджет и описание от 20 символов. Опубликуйте заказ.
4. Переключите кабинет на исполнителя. Свой заказ в общем поиске не показывается.
5. Заполните профиль и сохраните. Кнопка сохранения станет неактивной до новых изменений.
6. В другом браузере/приватном окне зарегистрируйте аккаунт B как исполнителя. Опубликованный заказ A должен появиться в поиске. Кнопок редактирования чужого заказа быть не должно.
7. Создайте еще один черновик у A: B не должен видеть его ни в поиске, ни по прямой ссылке.
8. Обновите страницу: аккаунт и выбранная роль сохраняются.

## Проверки разработчика

После перевода на nginx проверено: 5 тестов на PostgreSQL 16, миграции и повторный seed, сборка Next.js standalone, весь трафик через nginx (страницы, регистрация, вход, создание заказа, заголовки безопасности, лимит 429), HTTPS-конфигурация с тестовым сертификатом. Сборка самих Docker-образов в среде подготовки не выполнялась: Docker Hub был недоступен. Первый `docker compose up --build` на вашей машине — обязательная проверка.

Ранее:

Локально выполнены: 5 интеграционных API-тестов на SQLite с включенными внешними ключами, новая миграция на пустой базе, сравнение моделей и схемы, компиляция миграции в SQL PostgreSQL, Next.js production build, TypeScript и ESLint.

Полный контейнерный запуск и тесты на живом PostgreSQL в среде подготовки не выполнены. Браузерный E2E не выполнен: установка Chromium не удалась. Визуальная проверка на реальном браузере и проверка двух учеток по инструкции выше обязательны перед дальнейшим развитием.

Для запуска тестов на отдельном PostgreSQL:

```powershell
docker compose --profile test run --build --rm test
```

Тестовая база отдельная, временная. Никогда не указывайте рабочую базу в `TEST_DATABASE_URL`: тесты создают и удаляют таблицы.

## Архитектура и ограничения

- `app/modules/identity`: аккаунт, JWT и выбор текущего кабинета.
- `app/modules/workspaces`: одно личное пространство на аккаунт. Командные пространства пока не реализованы.
- `app/modules/marketplace/service.py`: проверка владельца, версии и возможности редактирования заказа.
- `app/modules/marketplace/router.py`: API заказов.
- `app/modules/profiles`: свой профиль исполнителя.
- `frontend/src/app/(workspace)`: кабинет, карточка заказа, редактор, профиль.
- `frontend/src/components/session.tsx`: оболочка кабинета и переключение ролей.
- `alembic/versions/0001_initial.py`: новая зафиксированная схема. Предназначена для пустой базы.

Текущая роль является настройкой интерфейса: оба действия доступны одному аккаунту. Защита основана на владении объектом, а не на переключателе. Все суммы первого этапа в KZT, в API передаются в тиынах. У опубликованного заказа пока нельзя менять условия. Портфолио и публичная страница профиля будут следующим расширением.

Это локальная версия разработки. До публичного запуска нужны: подтверждение email, восстановление доступа, серверное завершение сессий/обновление токенов и безопасная политика хранения сессии. Сейчас JWT хранится в localStorage, срок действия 12 часов; выход удаляет его из этого браузера.

Старые тесты, которые закрепляли открытый доступ и создавали несуществующие внешние ключи, заменены сценариями первого этапа. История старых миграций заменена целиком; обычный upgrade старой базы не поддерживается.
